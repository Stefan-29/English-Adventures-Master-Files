# Current architecture and canonical layout

## Layout decision

This is a vanilla JavaScript static site served from the repository root.
`package.json` identifies `app.js` as its entry point, and `npm run dev` serves
`.` so that root `index.html` can resolve `css/`, `modules/`, `config/`, and
`assets/` using the paths already used by the app. No application files were
moved; relocating them under `src/` would break those URLs and fetch paths.

`src/pages/` contains legacy copies of the legal pages. The canonical pages
linked by the app are in `legal/`. Keep the legal links and stylesheet paths
relative to those existing locations unless the page files are deliberately
consolidated.

## Current request and data flow

1. The browser requests root `index.html` and its stylesheets.
2. `ContentService` queries public topic metadata from the Supabase `topics`
   table.
3. Selecting a topic calls the authenticated `get-lesson` Edge Function; after
   entitlement checks, the function reads `{ config, data }` from private
   Storage and returns it without caching.
4. Feature code in `modules/` renders activities; local progress is stored in
   browser `localStorage`. Images and sounds are served from `assets/`.

The production flow now checks identity and entitlement server-side through
`get-lesson`; it is unavailable until Supabase, private Storage, and Upstash
are configured and deployed.

## Static hosting boundary

The development web root is the repository root. Static hosting makes every
deployed file publicly requestable; hiding a link, using a client-side check,
or storing a path in `localStorage` does not protect content. Production must
publish only the `dist/` output created by `npm run build`; that allowlisted
build excludes topic configuration and activity JSON. The repository source
files remain in the checkout, and the development server exposes them locally.
If the Git repository is public, the source files and their history are still
public; the `dist/` build is not a remedy for repository exposure.

The production bundle keeps only the public topic index interface and public
static assets; lesson/activity JSON is served only by the authenticated
Edge Function after server-side authorization.

## Supabase content access

The app loads public topic metadata from Postgres and calls the `get-lesson`
Edge Function for selected topic JSON. The function validates a verified user
and checks free-topic or active-enrollment access before reading from the
private `lesson-content` Storage bucket. It sends `Cache-Control: no-store`;
there is no service-worker cache in the app.

The private bucket is provisioned in Supabase and populated from the external
export generated by `scripts/supabase/export-content.js`. Never publish the
service-role key. See [the deployment guide](../setup/CONTENT_ACCESS_SETUP.md).

## Supabase schema groundwork

The initial schema migration is
[`20261023000000_initial_schema.sql`](../../supabase/migrations/20261023000000_initial_schema.sql).
It defines profiles, the public topic index, plans, enrollments, orders,
payments, progress, audit records, and student groups. Every table enables and
forces RLS. Client writes are limited to the authenticated user's own progress;
administrative and payment mutations are reserved for trusted Edge Functions.
Profile role and status updates are not granted to browser clients, and
administrative reads require an active, verified owner session with MFA
assurance level `aal2`.

The migration is source code only until it is applied to a Supabase project.
It does not yet implement Edge Functions, private Storage policies, payment
processing, or the admin interface.
